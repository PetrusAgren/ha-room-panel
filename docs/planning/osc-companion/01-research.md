## Companion findings

### Hosting within Home Assistant

The avdmr app is a plausible evaluation candidate. Its inspected manifest is app version 0.3.7 for amd64/aarch64. Its Dockerfile pins Companion 5.1.3 images by digest. run.sh stores configuration under /data/companion. The manifest publishes several control ports, leaves host_network commented, and has no Ingress declaration. The latest inspected repository commit is cfead230a97a7c607498ed29bcd29b6b3d0db01b, dated 15 November 2026. An inconsistent 38000/tcp description for its 8000/tcp web mapping needs checking. This is source evidence of packaging, with deployment validation still outstanding. [Manifest, Dockerfile and script](https://github.com/avdmr/bitfocus-companion-hass-addon/tree/main/bitfocus-companion)

BirdsLikeWires declares version 4.2.5-1, aarch64 only, with USB device mappings, persistent configuration and four TCP mappings. The latest inspected commit is ea5dbe26e708208970c7be047bf67320e28f41f1, dated 5 March 2026. Its manifest excludes an amd64 VM and declares no OSC listener mapping. Neither candidate has been installed or restore-tested here. Maintenance activity alone does not establish suitability. [Candidate source](https://github.com/birdslikewires/home-assistant-addons/tree/main/bitfocus-companion)

Recommend an optional, separately Supervisor-managed Companion app on the same HA machine. Room Panel remains one app with its own configuration UI. Keeping Companion in its own HA app gives it its existing update/export/backup lifecycle. Bundling its Node runtime and modules into Room Panel would expand image size, failure coupling and licensing/update responsibility. External Companion remains supported by changing its connection address. CPU/RAM figures require measurement with the real connection set. Test cold backups of both apps and export Companion configuration before upgrades.

### Supported interfaces and version differences

The documented HTTP Remote Control interface provides POST location press/down/up, variable read/write and connection status. Use page/row/column coordinates with an explicit UI preview. Avoid deprecated bank endpoints. It remains separate from the newer versioned API. [HTTP interface](https://companion.free/user-guide/v4.3/remote-control/http-remote-control/)

Companion 5.1 documents a versioned /api/v2 API, disabled by default, with locally served OpenAPI documentation. Its current documented areas include Connections and Surfaces. Do not promise complete CRUD/import of every page, button or action. Validate the running instance's schema before enabling management features. [REST API](https://companion.free/user-guide/v5.1/remote-control/rest-api/)

API v2 uses Bearer keys and scope checks. It exposes a way to list connection status and known surfaces. Configure a least-privilege key in Room Panel and keep it server-side. Do not infer legacy protocol protection from that key or the Admin UI password. [Authentication](https://companion.free/user-guide/v5.1/remote-control/rest-api/authentication/) · [Connections](https://companion.free/user-guide/v5.1/remote-control/rest-api/connections/) · [Surfaces](https://companion.free/user-guide/v5.1/remote-control/rest-api/surfaces/) · [Security](https://companion.free/user-guide/v5.1/security/)

Satellite provides TCP and WebSocket transports, BEGIN protocol negotiation, optional capabilities and heartbeat handling. Button subscriptions use ADD-SUB, SUB-STATE and SUB-PRESS when SUBSCRIPTIONS is advertised. Older servers can use a registered surface. Variables can carry continuous input/output, but typed JSON encoding requires API 1.16, documented for Companion 5.2+. The inspected app image is 5.1.3. Implement a negotiated subset and test numeric-string conversion. Rendered button appearance describes Companion feedback, with device confirmation determined by its module. [Satellite specification](https://companion.free/for-developers/Satellite-API/)

A Room Panel button can bind to a Companion instance and absolute location. Admin chooses a location manually or imports a bounded page export as a selection aid. Room Panel owns display label/appearance by default and can opt into live Companion label/color. Store the location binding and show a broken-binding diagnostic when the export is changed. Detecting every move automatically is an unresolved compatibility item.

Continuous Companion control is conditional. A custom/input variable must be consumed by an explicitly configured Companion action/trigger or supported module expression, and a separate output variable must report the actual device value. Writing a variable alone does not command an arbitrary mixer parameter. A +/− button pair provides relative control, but it cannot substantiate an absolute fader with a guaranteed mapped ceiling. Prototype one real module before advertising continuous support. [Variable endpoints](https://companion.free/user-guide/v5.1/remote-control/http-remote-control/) · [X32 module](https://github.com/bitfocus/companion-module-behringer-x32)

### Community bridge assessment

avdmr/Bitfocus-Companion-HA-Bridge documents exported-page import into button/switch/sensor entities, HTTP presses and observer-surface or subscription feedback. Switch state may be inferred from rendered appearance. It needs a Core custom integration and configuration import. Its README was inspected, but deeper source retrieval did not succeed, so authentication, version compatibility and runtime behavior remain unverified. Current Room Panel excludes these entity domains, so adopting the bridge alone would not make them appear. Evaluate as an optional HA route after domain support, not a mandatory Room Panel dependency. [Bridge documentation](https://github.com/avdmr/Bitfocus-Companion-HA-Bridge/blob/main/README.md)

Bitfocus's homeassistant-server module connects in the other direction, allowing Companion to operate HA. It can reuse existing HA actions, but is not a general Room Panel-to-Companion bridge. [Module source](https://github.com/bitfocus/companion-module-homeassistant-server)

## OSC findings

OSC specifies addresses, typed arguments and bundles, with int32, float32, strings and blobs as core types. It does not define universal mixer controls, discovery, state subscriptions or authentication. UDP carries packets conveniently, but recovery and acknowledgement need device-specific design. Preserve exact type tags and argument positions. A boolean tag and integer 0/1 can represent different device contracts. [OSC 1.0 specification](https://opensoundcontrol.stanford.edu/spec-1_0.html)

python-osc is the preferred library candidate. It provides builders, parsing and address dispatch, and its AsyncIOOSCUDPServer fits the current event loop. Pin and test a specific release against the app's Python runtime before adding it. Review dispatcher/timetag behavior to prevent future-dated bundles from blocking or scheduling unbounded work. A shared asyncio datagram endpoint using its codec is preferable when a device replies to the sending source port. No thread-per-packet architecture is needed. [Library](https://github.com/attwad/python-osc) · [Async server](https://python-osc.readthedocs.io/en/stable/server.html)

noodledostuff/ha-osc-control currently offers HA button/number controls. The inspected OSCEndpoint creates a SimpleUDPClient, converts a single value and sends through an executor. OSCNumber assigns its state after sending. These paths do not establish received device confirmation or a subscription lifecycle. Extending it would still require bidirectional transport and would add a Core installation to this app-first project. Use it as a reference and optional interoperability experiment. [Endpoint source](https://github.com/noodledostuff/ha-osc-control/blob/main/custom_components/ha_osc_control/osc_endpoint.py) · [Number source](https://github.com/noodledostuff/ha-osc-control/blob/main/custom_components/ha_osc_control/number.py)

Product profiles must distinguish transport, addressing, channel indexing, argument encoding, state queries, subscription renewals and fader law. The X Air Companion module explicitly describes a segmented fader law and quantization. A straight 0–1 conversion therefore cannot stand in for every product's dB behavior. Reusing verified protocol knowledge needs license review and hardware tests. Yamaha CL/QL, Soundcraft Ui and other equipment require their own protocol assessment. [X Air module documentation](https://github.com/bitfocus/companion-module-behringer-xair/blob/master/companion/HELP.md)

## HA networking and exposure

HA app networking supports declared TCP/UDP host mappings and optional host networking. Ingress is an HTTP streaming/WebSocket gateway. It cannot transport raw mixer UDP. Choose a bounded published UDP port set for fixed feedback listeners. For replies to the sending port, first validate a single bound bidirectional socket with the actual VirtualBox/NAT topology. When a device requires preserved source ports or multicast, evaluate an explicit host-network variant with documented port conflicts. [App configuration](https://contributors.home-assistant.io/apps/reference/configuration/) · [Ingress](https://developers.home-assistant.io/docs/apps/presentation/)

An app's HA WebSocket connection can call services and subscribe to state events, but creating a state entry alone does not implement a native entity with its services and lifecycle. Exposing Room Panel parameters as HA entities requires a Core integration or an optional discovery transport such as MQTT. Keep existing HA entities authoritative in the HA provider. [HA WebSocket API](https://developers.home-assistant.io/docs/api/websocket/) · [MQTT discovery](https://www.home-assistant.io/integrations/mqtt/)

## Architecture comparison

These are engineering estimates based on the inspected extension points. Performance rankings require benchmark confirmation.

| Criterion | A — Companion app and bridge | B — OSC in Room Panel | C — OSC Core integration | D — shared controls with HA, OSC and Companion providers |
| --- | --- | --- | --- | --- |
| Current code fit | Needs button/switch rendering or direct bridge | Fits aiohttp/asyncio process | Reuses HA client after adding domains | Fits through incremental wrapping of control.py |
| Complexity | Medium, two configs and adapter | Medium, device protocols owned here | High, Core package and app editor coordination | Medium-high, staged shared model and providers |
| Maintenance | Companion plus bridge/module compatibility | Library and product profiles | Core release compatibility plus profiles | Common policies once, three bounded adapters |
| Latency/faders | Indirect, module/expression dependent | Direct UDP path, most controllable | HA service/state round trips | Direct where needed, reusable UI |
| Feedback | Button appearance and module variables | Explicit queries/subscriptions per profile | Entity availability/state | Shared quality model with provider-specific evidence |
| Product reach | Broad installed Companion modules | Limited to validated profiles/generic OSC | Same protocol work as B | Existing modules plus direct profiles |
| Reliability | Companion restart affects its devices | App restart affects direct OSC | Core restart affects OSC | Per-provider availability and read-on-connect |
| UX | Familiar existing actions, extra Companion setup | Fully configured in Room Panel | Two setup locations | One Room Panel editor, optional Companion binding |
| HA integration | Good through bridge entities | Optional export required | Best native integration | Existing HA controls now, selected native exposure later |
| Security | Legacy ports need segmentation | UDP source/destination restrictions | Core integration has HA privileges | One panel authorization/policy boundary |
| Testing | API/version and button lifecycle | Codec/network/device/state tests | HA config flow/platform/unload tests | Shared contracts plus provider-specific tests |
| Migration | New dependency and imported entities | Additive app schema | Additional install/restart | Additive, keep legacy entity commands |
| Long-term cost | Module updates and adapter coupling | Owning every direct product | Owning profiles plus Core compatibility | More initial discipline, avoids duplicate policy paths |

Recommend D implemented in small stages, with B inside the existing Room Panel app and Companion as optional hosting or an external connection. Reuse the HA path first to prove mapping and UI. Add generic OSC next, then one qualified product profile and Companion buttons. Native HA entity export follows when needed. This preserves the app-based deployment and existing room workflow while enabling both integration routes.
